## 1. FINAL PRODUCT DEFINITION

### What Statecraft Is

Statecraft is a **cyber environment compiler and deterministic action engine**. A user provides a description of an organization's IT environment — in natural language, YAML, or from a template — and the system compiles that description into a structured, in-memory state machine. Attacker and/or defender agents (human or AI) then interact with that state machine through a constrained action grammar. The engine decides, by rule, whether every action succeeds, what changes, and what telemetry is generated.

The engine is always the authority. An agent can only observe state and propose actions. It cannot manufacture outcomes.

### Target Users (v1)

- Cybersecurity students learning attacker methodology in a structured environment.
- SOC/blue-team practitioners running tabletop-style exercises without standing up real infrastructure.
- Security researchers studying attack-path graphs and detection coverage across varied topology configurations.
- Developers building or evaluating AI security agents who need a ground-truth environment to measure against.

### Core Use Cases

- Compile a natural-language enterprise description into an attackable simulated environment.
- Step through an attack sequence (scan → exploit → pivot → exfiltrate) and have every step validated against the environment's actual state.
- Replay any completed run identically, or fork it at a chosen moment with a changed defensive posture.
- Measure detection coverage — which attacker actions were visible to which security controls, and when.
- Generate a narrative of what happened (LLM-assisted) grounded in the engine's event log, not invented.

### What Statecraft Is NOT

**Not a CTF platform.** CTF platforms present pre-built static challenges with hidden flags. Statecraft generates environments procedurally and the "objectives" are defined by the operator, not fixed in advance. There is no capture/submission loop.

**Not a pentesting framework.** Metasploit, Burp Suite, and their kin execute real actions against real targets over real networks. Statecraft never touches real infrastructure. Its "exploits" are state transitions, not shellcode.

**Not an LLM pentest agent.** Projects like AutoGPT-wrapped pentesting tools let the LLM decide whether an attack succeeds, producing impressive-looking but unverifiable output. Statecraft uses the LLM only where it belongs — text in, text out, with the simulation engine as the referee for everything that has a ground-truth answer.

**Not a VM-based cyber range.** Traditional cyber ranges (Cyber Polygon, NICE framework labs, vendor training environments) spin up real virtual machines, real operating systems, and real network stacks. They require significant infrastructure, cannot be trivially replayed or branched, and their state is opaque to systematic measurement. Statecraft's environments exist entirely as data structures. This is a deliberate constraint that enables everything else.

### The Core Differentiator

Statecraft is the only tool in this space where:
1. The environment is generated from natural language and is structurally validated before any interaction begins.
2. Action outcomes are computed by a deterministic rule engine, not generated by a language model.
3. Any run can be replayed identically from its seed and event log.
4. The observation model enforces information asymmetry — agents only see what they have discovered, not ground truth.

The system decomposes into two cleanly separated pipelines joined at the EnvironmentSpec.

### Component Specifications

---

#### 2.1 Input Layer

**Responsibility:** Accept scenario descriptions in any supported format and route them to the appropriate compiler path.

**Inputs:** Raw string (NL), file path (YAML/JSON), dataset path (CSV/structured), template ID.

**Outputs:** Normalized input object forwarded to the Scenario Compiler.

**NOT allowed to:** Pre-process content in ways that alter semantic meaning. No silent truncation.

---

#### 2.2 Scenario Compiler

**Responsibility:** Transform an input description into a draft `EnvironmentSpec` (Section 5). This is the only component in the system that uses an LLM.

**Inputs:** Normalized input from Input Layer + system prompt containing the full EnvironmentSpec JSON schema + vocabulary of allowed effect primitives + examples.

**Outputs:** Draft `EnvironmentSpec` (JSON). Labeled explicitly as `draft: true` until validated.

**Dependencies:** LLM client (OpenAI/Anthropic SDK), EnvironmentSpec schema (Pydantic), effect vocabulary.

**NOT allowed to:** Execute any simulation logic. Write to the State Store. Make decisions about whether actions succeed. The compiler's output is *always* treated as untrusted input by the Validation Engine.

---

#### 2.3 Validation Engine

**Responsibility:** Accept a draft `EnvironmentSpec` and either approve it, return structured validation errors, or request a repair pass.

**Inputs:** Draft `EnvironmentSpec`.

**Outputs:** `ValidationResult{valid: bool, errors: list[ValidationError], repaired_spec?: EnvironmentSpec}`. On approval, strips the `draft` flag.

**Validation pipeline (ordered):**
1. Schema validation (Pydantic)
2. Referential integrity (all IDs resolve)
3. Graph consistency (network topology is connected)
4. Reachability (attacker can reach at least one host from starting position)
5. Capability consistency (vuln preconditions reference only legal primitives)
6. Cycle detection (no circular trust dependencies that deadlock progression)
7. Solvability probe (optional in v1: BFS over action graph confirms path to objective)

**NOT allowed to:** Modify semantic content of the spec without logging the change as a repair. Use an LLM to make repair decisions.

---

#### 2.4 Simulation Engine

**Responsibility:** Accept a validated `EnvironmentSpec`, maintain the canonical ground-truth `EnvironmentState`, execute actions, apply state deltas, and emit events to the Telemetry Bus.

**Inputs:** Validated `EnvironmentSpec`, `Action` objects from agents.

**Outputs:** `ActionResult`, updated `EnvironmentState`, `Event` stream.

**Subcomponents:**
- **State Store:** Holds the current `EnvironmentState`. Exposes only a read-only view to agents (see Fog of War). Accepts only engine-internal writes.
- **Action Registry:** The canonical dictionary of all supported action types with their precondition predicates, effect functions, and telemetry specifications.
- **Action Executor:** The pure function `(State, Action) → (State', [Event], ActionResult)`. This is the most important function in the codebase.

**NOT allowed to:** Accept state mutations from any external caller. Allow agents to bypass the Action Executor. Use a language model for any decision.

---

#### 2.5 Agent Interface

**Responsibility:** Provide a clean, constrained API surface for attacker agents, defender agents, and human clients.

**Inputs:** `ProposedAction` (attacker), `DefenseAction` (defender), `ObservationRequest`.

**Outputs:** `ActionResult` (stripped of ground truth), `AgentObservation` (fog-of-war filtered).

**NOT allowed to:** Expose `GroundTruthState` directly. Let agents write to the State Store. Let agents introspect other agents' observations.

---

#### 2.6 Persistence / Replay Engine

**Responsibility:** Record every `Event` to an append-only log. Reconstruct any past `EnvironmentState` by replaying the log from the beginning or from a checkpoint.

**Inputs:** `Event` stream from Telemetry Bus; run IDs for replay requests.

**Outputs:** `EnvironmentState` at any event index, serialized run files.

**NOT allowed to:** Modify events in the log (append-only is an invariant). Store mutable state in a way that bypasses the event-sourcing reconstruction.

## 4. DOMAIN MODEL

All entities are Pydantic `BaseModel` subclasses unless stated otherwise. Properties marked `[immutable]` are set at entity creation and never updated in place; mutation happens by producing a `StateDelta` that the State Store applies to create a new snapshot.

Top-level container. The root of the spec.

| Field | Type | Notes |
|---|---|---|
| `id` | `UUID` | [immutable] Auto-generated |
| `seed` | `int` | [immutable] Determinism seed |

## 6. ACTION SYSTEM

Every action handler conforms to this interface:

```python
class ActionHandler(ABC):
    verb: ActionVerb  # Class-level constant

    @abstractmethod
    def check_preconditions(
        self, state: EnvironmentState, action: ProposedAction
    ) -> tuple[bool, FailureReason | None]:
        """Pure function. No side effects. Returns (ok, reason_if_failed)."""

    @abstractmethod
    def compute_effects(
        self, state: EnvironmentState, action: ProposedAction, rng: SeededRNG
    ) -> list[EffectSpec]:
        """Pure function. Returns effect list. Does not apply effects."""

    @abstractmethod
    def build_telemetry(
        self, state: EnvironmentState, action: ProposedAction, success: bool
    ) -> list[Event]:
        """Pure function. Returns events. Does not emit them."""
```

The `ActionExecutor` calls these in sequence, then applies effects and emits events. The handlers themselves never mutate state.

### Action Definitions

---

#### scan

**Purpose:** Discover hosts reachable from the actor's current network position.

**Targets:** A network ID.

**Preconditions:**
- Actor has at least one active position in a network that can route to the target network (checked against firewall rules).

**Effects on success:**
- `discover_asset(host_id)` for each host in target network reachable through firewall rules.
- Does NOT reveal services, OS, or accounts.

**Effects on failure:** None (scan that fails a firewall rule reveals nothing, not even that the host exists).

**Telemetry emitted:**
- `scan_attempt(actor, target_network)`
- `host_discovered(actor, host_id)` × N (emitted per discovered host)

**Cannot do:**
- Discover hosts on networks with no reachable path.
- Reveal service details (that's `enumerate`).
- Authenticate, exploit, or pivot.

---

#### enumerate

**Purpose:** Identify services, ports, and banners on a discovered host.

**Targets:** A host ID.

**Preconditions:**
- Target host is in attacker's `known_hosts`.
- Network path to host exists per firewall rules.
- Target host `is_online`.

**Effects on success:**
- `discover_service(service_id)` for each running service on the host.
- Service banners are added to attacker's observation (software name/version, not vulnerabilities).

**Telemetry emitted:**
- `enumeration_attempt(actor, host_id)`
- `service_discovered(actor, host_id, service_id)` × N

**Cannot do:**
- Reveal vulnerabilities (they're deduced from software version by the attacker's knowledge, not automatically disclosed).
- Reveal accounts or files.

---

#### authenticate

**Purpose:** Attempt to authenticate to a service using a known credential.

**Targets:** A service ID.

**Preconditions:**
- Service is in attacker's `known_services`.
- Service requires authentication (auth type ≠ `none`).
- Attacker has a credential in `known_credentials` compatible with the service's auth type.
- Network path to service exists.

**Effects on success:**
- `grant_session(host_id, account_id, privilege_level)` — a session at the privilege level of the account that owns the credential.

**Effects on failure (wrong credential):** None to state; one failure event emitted.

**Telemetry emitted:**
- `authentication_attempt(actor, service_id, account_id)`
- `authentication_success(...)` or `authentication_failure(...)`
- IDS rules may trigger on N failures within M ticks.

**Special behavior:** If credential `is_weak`, the engine allows a brute-force action variant (configured as `authenticate` with `params.brute_force: true`) that has a probability of success equal to a fixed `WEAK_CRED_GUESS_PROBABILITY` constant (v1: treat as 1.0 if `is_weak`, 0.0 otherwise).

---

#### exploit

**Purpose:** Attempt to exploit a vulnerability on a service.

**Targets:** A service ID.

**Preconditions:**
- Service is in attacker's `known_services`.
- Service has at least one vulnerability that the attacker has identified (vulnerabilities are discovered when the attacker possesses a service banner that version-matches a vuln in the vulnerability library).
- Network path exists.
- Attacker meets `required_capabilities` of the targeted vulnerability.
- Service `is_running`.

**Effects on success:**
- Apply the vulnerability's `effects` list as effect primitives.

**Effects on failure:**
- Nothing. Attempted exploitation is noisy regardless of success.

**Telemetry emitted:**
- `exploit_attempt(actor, service_id, vuln_id)`
- `exploit_success(...)` or `exploit_failure(...)`
- Detection controls evaluate based on `detection_probability` and active controls.

**Cannot do:**
- Succeed without meeting all preconditions.
- Produce effects not in the vulnerability's declared effect list.
- Bypass firewall rules.

---

#### escalate_privilege

**Purpose:** Elevate privileges on a host where the actor has an existing session.

**Targets:** A host ID.

**Preconditions:**
- Actor has an active session on the target host.
- The host has a priv-esc vulnerability AND the attacker has identified it.
- OR the attacker has discovered a local admin credential.

**Effects on success:**
- `elevate_privilege(session_id, new_privilege_level)`

**Telemetry emitted:**
- `privilege_change(actor, host_id, from_level, to_level)`

---

#### pivot

**Purpose:** Use an existing session on a host to project into another network segment.

**Targets:** A network ID, routed through a host where the actor has a session.

**Preconditions:**
- Actor has an active session on a host with a network interface in a network from which the target network is reachable (per firewall rules, evaluated from the pivot host's perspective, not the attacker's original position).

**Effects on success:**
- `pivot_network(from_host_id, to_network_id)` — attacker gains a position in the target network segment.

**Cannot do:**
- Bypass firewall rules that apply to the pivot host's egress.
- Grant sessions on targets in the new network (pivot only changes position; further scans/exploits are required).

**Telemetry emitted:**
- `lateral_movement(actor, from_host_id, to_network_id)`

---

#### access_data

**Purpose:** Read a data asset or file on a compromised host.

**Targets:** A data asset ID or file ID.

**Preconditions:**
- Actor has an active session on the host where the asset resides.
- Session's account is in the asset's `accessible_by` list OR session has `admin`/`root` privilege.

**Effects on success:**
- `read_file(file_id)` or `read_data_asset(asset_id)`.
- If asset/file `contains_credential_id`, also applies `obtain_credential`.
- If asset is a declared `Objective`, marks objective as achieved.

**Telemetry emitted:**
- `data_access(actor, host_id, asset_id, sensitivity)`

---

#### persist

**Purpose:** Establish a persistence mechanism on a compromised host.

**Targets:** A host ID.

**Preconditions:**
- Actor has an active session with `admin` or `root` privilege on the target host.

**Effects on success:**
- `create_persistence(host_id, actor_id)` — session survives simulated time-advance events.

**Telemetry emitted:**
- `persistence_created(actor, host_id)`

## 7. EFFECT PRIMITIVES

The effect system uses a **closed vocabulary of 12 primitives** for v1. Every vulnerability's effects and every action's outcomes must be expressible as a composition of these. No ad-hoc state mutations.

```python
class EffectPrimitive(str, Enum):
    grant_session           = "grant_session"
    elevate_privilege       = "elevate_privilege"
    revoke_session          = "revoke_session"
    obtain_credential       = "obtain_credential"
    discover_asset          = "discover_asset"
    discover_service        = "discover_service"
    pivot_network           = "pivot_network"
    read_file               = "read_file"
    read_data_asset         = "read_data_asset"
    create_persistence      = "create_persistence"
    disable_control         = "disable_control"
    achieve_objective       = "achieve_objective"
```

### Primitive Specifications

| Primitive | State Change | Inputs |
|---|---|---|
| `grant_session` | Adds `Session` to `EnvironmentState.sessions` | `host_id`, `account_id`, `privilege_level` |
| `elevate_privilege` | Updates `session.privilege_level` | `session_id`, `new_privilege_level` |
| `revoke_session` | Marks session `is_active = false` | `session_id` |
| `obtain_credential` | Adds `credential_id` to `actor.known_credentials` | `credential_id` |
| `discover_asset` | Adds host/asset ID to `actor.known_hosts` or `known_data_assets` | `asset_id`, `asset_type` |
| `discover_service` | Adds service ID to `actor.known_services` | `service_id` |
| `pivot_network` | Adds `network_id` to `actor.reachable_networks` | `network_id`, `via_host_id` |
| `read_file` | Adds file to `actor.accessed_files`; emits access event | `file_id` |
| `read_data_asset` | Adds asset to `actor.accessed_assets`; emits access event | `asset_id` |
| `create_persistence` | Marks host as persistent for actor | `host_id`, `mechanism_label` |
| `disable_control` | Sets `control.is_active = false` | `control_id` |
| `achieve_objective` | Sets `objective.is_achieved = true`, records tick | `objective_id` |

### Composition

A vulnerability effect list is an ordered sequence of `EffectSpec` objects:

```python
class EffectSpec(BaseModel):
    primitive: EffectPrimitive
    params: dict
    condition: str | None  # If set, only apply if this condition holds in current state
```

The `EffectComposer` takes an `EffectSpec` list and returns a `StateDelta`. Order matters — later effects may depend on state produced by earlier ones (e.g., `grant_session` before `elevate_privilege` in a combined effect).

### Why this vocabulary is sufficient for v1

- **Attacker wins** by: `obtain_credential` + `grant_session` + `pivot_network` + `read_data_asset` + `achieve_objective`.
- **Attacker maintains** by: `create_persistence`.
- **Attacker weakens defense** by: `disable_control`.
- **Defender wins** by: `revoke_session` (v2 active defender action).
- All realistic v1 attack paths (initial access → foothold → lateral movement → exfiltration) are expressible in this set.

What this vocabulary intentionally cannot express in v1: write-file (file system modification), modify-firewall, DoS (service state change beyond disable_control). These are v2 additions.

## 8. VALIDATION ENGINE

### Pipeline (ordered — fail fast)

```
Stage 1: Schema Validation
  - Pydantic model_validate(spec_dict)
  - All required fields present, types match, enums valid
  - Fail type: SchemaError

Stage 2: Referential Integrity
  - Every ID referenced in any field (network_id, host_id, credential_id, etc.)
    resolves to a declared entity
  - No dangling foreign keys
  - Fail type: IntegrityError

Stage 3: Graph Consistency
  - All hosts have an IP within their network's CIDR
  - No two hosts share an IP on the same network
  - All firewall rules reference existing networks or hosts
  - Security controls reference existing hosts or networks
  - Fail type: GraphError

Stage 4: Reachability
  - Attacker's initial position can reach at least one host
    (firewall rule traversal from initial_attacker_position)
  - At least one host has at least one running service
  - At least one service is reachable from the attacker's position
  - Fail type: ReachabilityError

Stage 5: Capability Consistency
  - Every vulnerability's effects use only primitives in the closed vocabulary
  - Every vulnerability's required_capabilities uses only defined CapabilityType values
  - Every control's detects reference valid action verbs
  - Fail type: CapabilityError

Stage 6: Cycle Detection
  - Trust relationship graph has no cycles of type credential_reuse
    (to prevent circular credential dependencies)
  - Fail type: CycleError

Stage 7: Solvability (optional, v1)
  - BFS over action graph: starting from initial_attacker_position,
    assuming omniscient attacker, can at least one Objective be achieved?
  - If no path to any objective exists, emit a warning (not hard fail in v1)
  - Fail type: UnsolvableWarning (soft)
```

### What Constitutes an Invalid Environment

An environment is **hard-invalid** if it fails stages 1–6. The validator will not produce a simulation from it. Hard invalidity examples:

- A host's `network_id` references a network not in `spec.networks`.
- Two hosts share `10.0.1.10` on `net.dmz`.
- A vulnerability effect uses a primitive not in the closed vocabulary (e.g., `run_arbitrary_code`).
- A trust relationship creates a circular credential dependency: A reuses B's cred, B reuses A's cred.
- The attacker's starting position has no firewall rule permitting any traffic anywhere.

An environment is **soft-invalid** if it fails stage 7 only: it's structurally valid but the attacker cannot logically achieve any declared objective from the starting position. This is emitted as a warning, allowing a "sandbox" environment with no defined objectives.

### GENERATE → VALIDATE → REPAIR Loop

```python
MAX_REPAIR_ATTEMPTS = 3

def compile_and_validate(natural_language_input: str) -> EnvironmentSpec:
    draft = compiler.compile(natural_language_input)

    for attempt in range(MAX_REPAIR_ATTEMPTS):
        result = validator.validate(draft)

        if result.valid:
            return result.spec

        if attempt < MAX_REPAIR_ATTEMPTS - 1:
            # Feed structured errors back to compiler for repair
            draft = compiler.repair(draft, result.errors)
        else:
            raise CompilationFailedError(result.errors)
```

The `repair()` call sends the original spec and the list of `ValidationError` objects (not raw text — structured error types with entity IDs and violation descriptions) back to the LLM with a repair-focused system prompt. The LLM is instructed to return only the corrected spec, not commentary.

## 9. DETERMINISTIC SIMULATION

### Invariant

> For any `(EnvironmentSpec, seed, action_sequence)` tuple, the resulting `(final_EnvironmentState, event_log)` is always identical.

This invariant must be testable and tested.

### State Store

```python
class StateStore:
    _snapshots: list[EnvironmentState]  # append-only
    _current_index: int

    def apply_delta(self, delta: StateDelta) -> EnvironmentState:
        """Creates new snapshot. Never modifies existing ones."""
        new_state = deep_copy(_snapshots[_current_index])
        new_state = _apply(new_state, delta)
        new_state.tick += delta.tick_advance
        _snapshots.append(new_state)
        _current_index += 1
        return new_state

    def state_at(self, tick: int) -> EnvironmentState:
        """Read-only access to historical state."""
        return _snapshots[tick]

    def current(self) -> EnvironmentState:
        return _snapshots[_current_index]
```

Key: `_snapshots` is append-only. There is no `update_state(index, ...)` method. The only mutation primitive is `apply_delta`, which always extends the list.

### Seeded RNG

```python
class SeededRNG:
    def __init__(self, seed: int):
        self._rng = random.Random(seed)
        self._call_count = 0

    def roll(self, probability: float) -> bool:
        self._call_count += 1
        return self._rng.random() < probability
```

`SeededRNG` is instantiated once per simulation run from `environment.seed`. It is passed to `ActionHandlers.compute_effects()` only for probabilistic outcomes. In v1, all reliabilities are 1.0, so the RNG is never called — the seed is still required in the spec for v2 compatibility.

**Critical:** RNG call count must be consistent across replay. Any code path that conditionally calls the RNG (e.g., "call RNG only if control is active") creates a divergence bug. Every probabilistic check must always consume exactly one RNG sample, then check the result — never skip the call based on context.

### Action Execution Transaction

```python
def execute(self, action: ProposedAction) -> ActionResult:
    state = self.state_store.current()

    # Stage 1: Grammar check (synchronous, no state read)
    if not self.action_registry.is_valid_verb(action.verb, action.actor_id):
        return ActionResult(success=False, failure_reason=FailureReason.forbidden_by_grammar, ...)

    # Stage 2: Get handler
    handler = self.action_registry.get(action.verb)

    # Stage 3: Preconditions (pure read of state)
    ok, reason = handler.check_preconditions(state, action)
    if not ok:
        events = handler.build_telemetry(state, action, success=False)
        self.telemetry_bus.emit_all(events)
        self.event_log.append_all(events)
        return ActionResult(success=False, failure_reason=reason, state_delta=StateDelta.empty(), events=events)

    # Stage 4: Compute effects (pure, uses RNG)
    effect_specs = handler.compute_effects(state, action, self.rng)

    # Stage 5: Compose effects into delta
    delta = self.effect_composer.compose(state, effect_specs)

    # Stage 6: Apply delta (creates new snapshot)
    new_state = self.state_store.apply_delta(delta)

    # Stage 7: Build and emit telemetry
    events = handler.build_telemetry(state, action, success=True)
    self.telemetry_bus.emit_all(events, new_state)
    self.event_log.append_all(events)

    return ActionResult(success=True, state_delta=delta, events=events, ...)
```

This is one logical transaction. No partial application is observable externally.

class ObservationEngine:

## 12. REPLAY / BRANCHING

### Design: Event Sourcing

```
EnvironmentSpec (initial params)
+
[Event_0, Event_1, Event_2, ..., Event_N]
=
EnvironmentState at tick N
```

`state_at(N) = fold(initial_state, events[0:N+1])`

This works because every `Event` contains enough information to reconstruct the `StateDelta` that produced it. (In practice, we store the `StateDelta` directly in the event log for performance — the fold is then just re-applying deltas.)

### Schema: Run File

```python
class Run(BaseModel):
    id: UUID
    environment_spec: EnvironmentSpec    # Immutable snapshot of the spec used
    seed: int                            # RNG seed
    created_at: datetime
    events: list[Event]                  # Append-only
    state_checkpoints: dict[int, EnvironmentState]  # Every N events, for fast seeking
```

### Replay API

```python
class Replayer:
    def replay_to(self, run: Run, tick: int) -> EnvironmentState:
        # Find nearest checkpoint before tick
        checkpoint_tick = max(t for t in run.state_checkpoints if t <= tick)
        state = run.state_checkpoints[checkpoint_tick]
        # Re-apply deltas from checkpoint to target tick
        for event in run.events[checkpoint_tick:tick]:
            state = apply_delta(state, event.delta)
        return state
```

### Branching (design now, implement in v2)

```python
class Branch(BaseModel):
    parent_run_id: UUID
    fork_at_tick: int
    modified_spec_delta: SpecDelta | None  # e.g., changed firewall rule
    branch_events: list[Event]
```

A branch is a new `Run` whose initial state is `parent_run.replay_to(fork_at_tick)`, with a (optionally) modified spec applied on top. Branch resolution always reconstructs from parent first, never stores a full copy. This ensures efficient storage even with many branches.

**v1 stub:** Implement `Run` and `Replayer`. The `Branch` class is defined in the model but no fork operation is exposed until v2.

### Portable Run Export (.scr format)

```
university-attack-run-001.scr (gzipped tar)
├── manifest.json     { version, created_at, environment_id, event_count }
├── spec.yaml         { the EnvironmentSpec }
├── events.jsonl      { append-only event log, one event per line }
└── checkpoints/
    ├── tick_0000.json
    ├── tick_0050.json
    └── tick_0100.json
```

Any Statecraft instance can import a `.scr` file and replay or fork it.

## 17. TECHNOLOGY DECISIONS

### Python 3.12+

**Decision: Yes, for the entire v1 codebase.**

Rationale: The simulation engine's performance constraints are trivial (dozens of hosts, hundreds of events). What matters is velocity, expressiveness of the type system, ecosystem for LLM integration, and accessibility to contributors. Python's Pydantic-driven modeling, structural pattern matching (used in the action executor), and mature test tooling (pytest + Hypothesis) make it the right choice. A future v2 could extract the `engine/` core as a Rust library with Python bindings if hot-path performance becomes a real concern — the clean API boundary makes this possible without a full rewrite.

### Pydantic v2

**Decision: Yes, as the universal modeling layer.**

Pydantic serves three roles: domain model validation, EnvironmentSpec schema generation (for structured LLM output), and API request/response schemas. Using one library for all three removes the mismatch bugs that arise when you maintain separate schema definitions.

### SQLite

**Decision: Yes, for persistence.**

The event log is an append-only SQLite table. State checkpoints are serialized as JSON rows. This is inspectable, portable (the `.scr` export contains the SQLite file), and sufficient for any realistic scenario size. No ORM — raw SQL via `sqlite3` module for the event log, keeping the persistence layer thin and transparent.

### FastAPI

**Decision: Yes, for the API layer — but don't build it until Phase 8.**

When the CLI works end-to-end, add FastAPI on top of the same simulation functions. The CLI and API share the same service layer; FastAPI just exposes it over HTTP. This matters for the eventual web UI and for external agent integrations.

### CLI: Typer + Rich

**Decision: Typer** for command structure (auto-generated help, type-safe arguments, built on Click), **Rich** for terminal output (colored event timeline, host/service tables, progress bars during compilation). The demo's visual quality is important — Rich makes the output look like a real security tool without requiring a GUI.

### LLM Interface: Instructor (anthropic or openai SDK)

**Decision: Use the Instructor library (jxnl/instructor)** to enforce structured output from the LLM. This wraps the underlying SDK and retries automatically on schema violations. The compiler and attacker agent both use Instructor with Pydantic models as the output schema. This eliminates JSON parsing fragility.

### Graph Visualization

**Decision: Defer to v2.** The v1 CLI renders state as Rich tables. For v2, Cytoscape.js in a minimal FastAPI/HTML frontend renders the network topology and animates compromised-host state changes. Do not add vis.js or a separate graph lib to the v1 dependency tree.

### Testing: pytest + Hypothesis + pytest-cov

**Decision: Standard stack.** Hypothesis for property tests (determinism, vocabulary closure). Coverage gate: engine/ must be ≥ 95% before MVP is declared complete.

### Serialization: stdlib `json` with Pydantic `.model_dump_json()`

**Decision: No additional serialization library.** Pydantic handles all serialization needs. Events in the SQLite log are stored as `model_dump_json()` strings. Fast, correct, no dependency.

## 18. SECURITY MODEL

This is cybersecurity software with a trust model that must be explicit.

### Trust Boundaries

| Component | Trust Level | Reason |
|---|---|---|
| Simulation Engine core (`engine/`, `actions/`, `effects/`) | **Fully trusted** | Pure functions, no external I/O, author-controlled |
| Validation Engine | **Fully trusted** | Pure functions, deterministic |
| Domain model (`model/`) | **Fully trusted** | Pure data |
| Human CLI input | **Partially trusted** | Validates through Action grammar; cannot directly mutate state |
| LLM compiler output | **Untrusted** | Always goes through Validation Engine before use |
| LLM attacker agent output | **Untrusted** | Always goes through Action Executor precondition checks |
| Imported `.scr` scenario files | **Untrusted** | Schema-validated before use; no code execution from files |
| External datasets for generation | **Untrusted** | Treated as input to the Compiler, same pipeline as NL |

### Threat Model

**Can an attacker cause real harm by running Statecraft?**
No. The engine has no network stack, no system calls to real hosts, no packet generation. The only external I/O is LLM API calls and SQLite reads/writes. A malicious `EnvironmentSpec` file can at worst produce a logically invalid environment (rejected by the validator) or waste LLM API credits.

**Can a malicious LLM response break the engine?**
Not if the Validation Engine is correct. The LLM's output is schema-validated before any simulation code sees it. An adversarially crafted spec with a billion hosts would be caught by the reachability stage before any simulation runs.

**Can a maliciously crafted `.scr` file cause issues?**
The loader must validate the embedded spec through the full validation pipeline before instantiating a run. It must not `eval()` or dynamically execute any content from the file. Effects are data (`EffectSpec`), not code.

**Can the LLM learn to bypass simulation rules through repeated interaction?**
No. The LLM proposes `ProposedAction` objects. The Action Executor is deterministic code that ignores everything except the action's verb, target, and parameters. The LLM cannot negotiate, argue, or persuade the engine — it can only submit valid actions and receive results.
